# How Apogee generates a seed phrase

Where the randomness behind your wallet comes from, what protects the phrase once it
exists, and what that does and doesn't cover.

Written because it's a fair question to ask of any wallet, and a pointed one to ask in
2026: recovery phrases generated by some hardware wallets turned out to be predictable, and
that kind of flaw cannot be patched afterwards. If a phrase was generated weakly, the keys
themselves are weak, and a software update changes nothing.

For the full trace with line references, see
[`audits/entropy-and-seed-generation.md`](../audits/entropy-and-seed-generation.md).

## What happens when you create a wallet

One call, into a library Blockstream maintains:

| Step | Where |
|---|---|
| You choose "Create a new wallet" | side panel |
| The extension asks its engine for a 12-word phrase | `background/index.ts` |
| The engine calls `Mnemonic.fromRandom(12)` | `engine/engine-core.ts` |
| Liquid Wallet Kit (Blockstream's, compiled to wasm) asks the browser for random bytes | `lwk_wasm` |
| The browser's cryptographic random number generator produces them | your browser |

Apogee writes no random number generator of its own and makes no choice about the
entropy — it asks LWK for a phrase and receives one. Key derivation is likewise LWK's:
standard BIP-84, so the same phrase restores in Blockstream Green, Jade, and other standard
Liquid wallets.

**12 words is 128 bits of entropy** under BIP-39. That is the standard strength for a
12-word phrase and is not a shortcut; 24-word phrases (256 bits) can be restored, though
new wallets are currently created with 12.

## Where the randomness comes from

`crypto.getRandomValues` — the browser's own cryptographic generator, the same primitive
that protects TLS connections. Apogee reaches it through LWK rather than directly.

Two things about that path are worth stating plainly, because they are the two ways this
goes wrong in practice:

- **There is nothing weak to fall back to.** The compiled LWK module can only obtain
  randomness through the functions it imports from the browser, and the only ones it
  imports are the cryptographic ones. There is no ordinary `Math.random`-style generator
  bundled inside it that a misconfiguration could silently switch to.
- **If the generator were missing, generation fails.** The call is wrapped so that an
  error propagates as an error. You would get a failure, not a wallet built from zeros or
  from a half-filled buffer.

`Math.random` — the ordinary, non-cryptographic one — does appear in Apogee: 19 calls across
18 lines. Eighteen of them draw the night sky behind the UI (where each star sits, how a
meteor moves and how often), and one is in a test that never ships. It is never used for
anything to do with keys.

## What protects the phrase once it exists

Your phrase is encrypted before it touches disk, using a key derived from your password:

| | |
|---|---|
| Password stretching | PBKDF2-HMAC-SHA256, 600,000 iterations |
| Encryption | AES-GCM-256 |
| Salt | 16 random bytes, generated once when you set your password |
| Nonce | 12 random bytes, fresh for every encryption |
| Tamper detection | the wallet id is bound into the ciphertext, so a swapped record fails to decrypt |

The high iteration count exists to make a weak password expensive to attack. It is not a
substitute for a good one.

If you hold more than one wallet, they share a single password and a single derived key —
the salt belongs to the vault, not to each wallet. What keeps one wallet's encrypted phrase
from being swapped into another's slot is that each record is bound to its own wallet id,
and a swapped record fails to decrypt.

The phrase is never written anywhere in the clear, and no log line in the codebase prints a
phrase, a seed, or a password. Hardware wallets store no phrase in Apogee at all — Jade
keeps its own.

## Is Apogee affected by the Coldcard issue?

No. That was a firmware defect in a specific hardware product; Apogee shares no code with
it. More usefully, the two specific failure modes behind it don't exist here:

| The defect | Apogee |
|---|---|
| A build error silently switched to a non-cryptographic generator seeded from device serial numbers and timers | No such generator is present to switch to, and a missing generator causes a failure instead |
| 40 bytes of entropy were hashed and only the first 4 bytes used, capping the possibilities at about 4 billion | Random values are used at full width and never truncated on any key path |

**If you are moving funds off an affected device, generate a fresh phrase — do not restore
the old one into Apogee.** Restoring carries the weak keys across. This is the one action
that matters, and no wallet can fix it for you.

## What this does not cover

Being straightforward about the limits, because a security document that claims none is
worth less:

- **The browser's generator is trusted, not verified.** Apogee confirms it is asking the
  right thing in the right way. It cannot audit the generator inside your browser. Every
  software wallet in a browser shares this.
- **One source, not many.** A hardware wallet like Jade mixes several independent sources
  of randomness so that no single weak one can spoil the result. A browser extension has no
  hardware generator, no CPU counters, no uninitialized memory to draw on, so Apogee
  depends on the browser's generator alone. That is the correct primitive available in this
  environment — but it is one source rather than several.
- **No BIP-39 passphrase yet.** Some wallets support an extra secret on top of the phrase.
  Apogee does not currently offer one.
- **Your device is the boundary.** An unlocked wallet keeps the phrase in memory so it can
  sign, and no browser extension can defend against malware already running as you. Locking
  clears it.
- **Receive addresses are not confirmed on a hardware device.** Apogee shows you a receive
  address that it derived itself, on any wallet type including Jade. Jade shows you where
  funds are *going* when you approve a send, but it is not asked to confirm an address you
  are about to share. Do not assume that using a hardware wallet checks a receive address
  for you here.

**If you want your keys generated and held outside the browser, use a Jade.** Apogee
supports it as an external signer: the phrase is never created by or stored in the
extension, and the device shows the destination and amount before you approve a send. That
is the strongest configuration this wallet offers — with the receive-address caveat above.

short version:

